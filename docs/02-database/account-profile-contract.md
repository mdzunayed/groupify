# Account, profile and lifecycle contract — review draft

**2026-11-14 implementation note:** the separate [account authorization foundation](account-authorization-foundation.md)
now implements a narrower internal account/link schema and transaction boundary.
The protected [development bootstrap](../03-api/development-account-bootstrap.md)
now exposes a narrower identity-derived account-ID response. It does not implement
or accept this complete candidate model, profile policy or lifecycle recommendations.
The absence-of-migrations statements below describe the original full draft.

**Status: proposed, not implemented or accepted.** No table, migration, endpoint,
permission, recovery mechanism or retention exception is created by this document.
The separate [draft OpenAPI](../03-api/account-profile.draft.openapi.json) is not
the [implemented development HTTP contract](../03-api/openapi.json). Review this draft against
[PR-03/PR-18](../00-product/product-requirements.md), OD-17/OD-20 and ADR-015/018.

## Binding baseline and proposed boundary

Approved: profiles support name, picture and rider type, with optional vehicle
information; deletion deactivates immediately, permits 30-day recovery, then
permanently deletes personal data subject to legally required retention. Detailed
location history has its own 30-day retention rule. Roles remain Leader, Co-leader
and Member. Clerk is approved for development only.

Proposed: server UUID account IDs, exact provider/issuer/subject identity links,
self-service profile operations, transactional account-state checks, versioned
profile writes and a server-owned deletion cycle. These are reviewable technical
and permission choices, not inferred approval of profile visibility or recovery.
The current external-session verifier grants none of these capabilities.

## Candidate data model

All UUIDs are generated by the backend, never accepted as identity from a caller.
Store timestamps as PostgreSQL `timestamptz` and serialize UTC RFC 3339. Store
versions as positive `bigint`; serialize decimal strings to avoid JavaScript
integer precision loss. No phone number, OTP, JWT, secret or raw provider claims
belong in these tables. Hashes and indirect identifiers may still be personal data.

| Table | Exact candidate fields | Constraints and meaning |
| --- | --- | --- |
| `accounts` | `id uuid`, `state text`, `authorization_epoch bigint`, `version bigint`, `created_at timestamptz`, `updated_at timestamptz`, nullable `deletion_cycle_id uuid`, `deletion_requested_at timestamptz`, `recovery_until timestamptz`, `purge_started_at timestamptz` | PK `id`; state is `active`, `deactivated` or `purging`; epoch/version start at 1 and increase on security/lifecycle transitions. Active rows have no current deletion-cycle fields. Deactivated rows have cycle/request/deadline, with no purge start. Purging rows retain that cycle plus a purge start. State/timestamp combinations require DB checks. |
| `external_identities` | `id uuid`, `account_id uuid`, `provider text`, `issuer text`, `subject text`, `created_at timestamptz` | PK `id`; FK account with `ON DELETE RESTRICT`; unique `(provider, issuer, subject)`. Initially bootstrap only; no link/unlink/merge endpoint. Never match accounts by phone alone. Multiple links can be represented without inventing a user-facing linking policy. |
| `rider_profiles` | `account_id uuid`, `display_name text`, `rider_type text`, nullable `vehicle_description text`, nullable logical `photo_asset_id uuid`, `version bigint`, `created_at timestamptz`, `updated_at timestamptz` | PK/FK account with `ON DELETE RESTRICT`; one profile per account; type is `motorcycle` or `bicycle`. Name/type required when a profile exists. Photo ID is a logical owned-asset reference, not an arbitrary URL; its physical FK/storage table awaits the asset contract. No migration may leave ownership unenforced. |
| Operational records — not yet a physical schema | purpose-bound reauthentication proofs, idempotency results, deletion work/checkpoints, scoped legal holds, restore/deletion ledger | Needed before lifecycle endpoints/workers. Their retention, proof expiry/replay rules, provider evidence and backup handling need decisions below; do not silently create indefinite audit/identifier retention. |

Proposed DB checks also require positive epoch/version, a complete deletion-cycle
field set, deadline after request, and purge start no earlier than the deadline.
After R3 acceptance, enforce its exact deadline calculation as well. Account IDs
are immutable. Account-owned rows are deleted explicitly by reviewed erasure work;
FK restrictions must prevent accidental account-row removal or premature identity
reuse. Do not add cascading deletion into shared records.

No account row means no account access. A valid external session must not create
an account implicitly while handling an arbitrary protected request. Explicit
bootstrap atomically creates account/link, or resolves the existing exact link.
A duplicate-link race rolls back the losing creation and resolves the winner;
no orphan account, second identity mapping or phone-based merge is allowed.
Bootstrap must not reactivate a deactivated/purging account.

Profile existence is separate from account lifecycle. An account may exist before
its profile is created. Do not call a profile complete, gate unrelated capabilities,
or waive the picture requirement merely because a photo reference is null: picture
requiredness/timing and asset delivery remain review decisions.

## Proposed field semantics

- `displayName`: Unicode NFC, trim surrounding whitespace, preserve internal
  spelling/spacing/punctuation, reject control characters, 1–80 Unicode code points.
  This proposed engineering bound is not an approved product limit; JS UTF-16
  length must not accidentally differ from the database's character count.
- `riderType`: one of `motorcycle`, `bicycle`; support for both simultaneously is
  not silently inferred. Confirm this representation under OD-20.
- `vehicleDescription`: optional plain text, NFC/trim, no control characters,
  at most 160 code points; explicit null clears it, omission preserves it on PATCH.
  Empty normalized text becomes null. No plate/document/location fields are added.
- `photoAssetId`: read-only in this first draft of profile text operations.
  Photo upload/attachment requires a separate owned-asset, media validation,
  access and deletion contract. No client-supplied URL or unverified asset ID is
  accepted as a shortcut. Nullable storage is not approval to omit profile pictures.
- Unknown or immutable request properties are rejected. PATCH requires at least
  one mutable property. Bodies have no role, account ID or provider identity field.

## Self-service API proposal

**Every operation below is absent from the running backend.** Proposed bearer
identity verification must be followed by account-state/resource checks. The
production provider is not selected by the generic draft bearer scheme.

| Operation | Proposed behavior |
| --- | --- |
| `POST /v1/accounts/bootstrap` | Identity-derived, idempotent explicit bootstrap; 201 newly created, 200 existing active account. Deactivated/purging link returns 403, never a fresh replacement account. No body-supplied subject/account ID. |
| `GET /v1/me` | Minimal lifecycle summary for the mapped self: ID, state, version and current deletion cycle/deadline when applicable. No profile/phone/provider claims. Allowing this limited self-service read while inactive requires review; it grants no product activity. |
| `POST /v1/me/profile` | Active self only; create one profile from required name/type and optional vehicle description; 201 or 409 if it exists. Photo storage remains blocked. |
| `GET /v1/me/profile` | Active self only; 200 profile or 404 when absent. No `/users/{id}` lookup, leader editing or community-wide visibility is proposed. |
| `PATCH /v1/me/profile` | Active self only, existing profile, strong `If-Match` ETag; reject missing precondition (428), stale version (409), immutable/unknown fields (400). Omitted fields unchanged; explicit vehicle null clears it. |
| `POST /v1/me/deletion` | Verified self plus approved action-bound reauthentication proof; atomically deactivate and create one deletion cycle. 202 means durable deactivation and scheduled erasure, not completed deletion. Repeated calls cannot extend the deadline. |
| `POST /v1/me/recovery` | Explicit self recovery with fresh, approved, purpose/cycle-bound proof and current cycle ID; only before the deadline, under a row lock. 200 on successful activation. Never recover automatically during login/bootstrap. |

All self responses use `Cache-Control: no-store` and server `X-Request-Id`.
Profile responses carry a strong ETag such as `"profile-7"`; a concurrent profile
write or photo mutation must change its version. Compare owner/account/version
in the same transaction as the write, not in a client-side read first.

Every POST/PATCH requires `Idempotency-Key` (proposed UUID). Scope its digest by
account or verified identity, operation, body hash and deletion cycle when relevant.
Authenticate again on replay; reject mismatched body or later-cycle reuse with
409. Never persist/log proofs or credentials in cached payloads. Replays must not
return an obsolete active-state assertion after a later deletion. On replay, verify identity/account/cycle first, then resolve the accepted operation
without re-consuming its one-use proof. A first attempt must validate and consume
the proof atomically with its state transition; retries must not turn an expired
or consumed proof into a new transition. Exact record expiry is unresolved; do not invent a TTL that permits duplicate lifecycle effects
or retains identifying data indefinitely.

Errors reuse the safe HTTP envelope. The draft's 428 uses existing fallback
`REQUEST_FAILED`; 400/401/403/404/409/503 use the implemented generic codes. It
introduces no raw validation arrays or sensitive account-existence messages.
A timeout/offline UI must report an unconfirmed request until the server confirms
commit; neither a local button press nor a 202 proves all data was erased.

## Lifecycle transaction rules

Proposed clock: capture one database-clock value after taking the account row lock.
Use it as `deletion_requested_at`; compute `recovery_until = t0 + interval '720 hours'`
(30 elapsed UTC days). This exact clock/boundary interpretation needs review.
Commit, not request arrival, is the authorization change; respond only after commit.
A rolled-back request cannot be described as deactivated.

| Current state | Action and condition | Atomic result |
| --- | --- | --- |
| Active | Accepted deletion with approved proof | New cycle ID, deactivated state, fixed t0/deadline, increment account version and authorization epoch, durable invalidation/erasure work |
| Deactivated | Repeated accepted deletion | Preserve cycle and original deadline; do not restart or extend 30 days |
| Deactivated | Explicit recovery, valid purpose/cycle proof, database time strictly before deadline | Active; increment version/epoch, invalidate proof and cycle work, clear current cycle fields; old queued jobs must become harmless |
| Deactivated | Deadline reached or passed | Recovery denied immediately even if the worker is delayed; worker claims the same cycle as purging under lock |
| Purging | Recovery/bootstrap/product action | Denied; retries do not undo irreversible work |
| Purging | All required erasure steps confirmed, scoped legal exceptions handled under approved policy | Finalize deletion only with recorded completion evidence. Physical row removal, identity tombstones and backup/restore suppression depend on the approved retention contract. No permanent `purged` row is assumed to be anonymous. |

A worker and recovery racing at the boundary serialize on account row/cycle. At
exactly `recovery_until`, recovery loses. Worker claims include cycle/version;
recheck before every irreversible external step and ignore stale pre-recovery work.
Use retryable, durable work/checkpoints for provider/media erasure and distinguish
request acceptance from confirmed deletion. A service failure does not extend the
recovery window or justify leaving deletion silently overdue.

For product writes, hold the account's authorization read/lock in the same
transaction as the write so accepted deactivation orders against earlier work.
All HTTP, WebSocket and media consumers must check current active status and the
authorization epoch; a once-verified JWT or cached principal is insufficient.
Server commit blocks new authorized server activity; it does not prove an offline
device received invalidation or erased cached data. Track delivery/cleanup separately
and do not promise an instantaneous remote wipe. Recovery issues no membership/role
changes and never automatically enables GPS or PTT. Explicit active-ride join and tracking opt-in still apply.

## Shared records and erasure

Immediate deactivation must not wait for leadership succession or an open SOS.
Do not invent a fourth role, automatically promote a member, auto-resolve SOS,
or keep an account active to avoid an unresolved shared-record rule. The exact
handover, orphan-record presentation and safety-notification behavior need review.
Before allowing communities/rides, implement authorization invalidation for their
sockets/media/queued actions; account state alone does not terminate a transmitter.

| Data category | Requirement / unresolved boundary |
| --- | --- |
| Account/profile/vehicle and identity link | Needed only for the recovery window and explicit approved obligations; then erasure/identity reuse rules must be enforced. No automatic phone linking or old-token rebootstrap after purge. |
| Photos and derivatives | Owned originals, variants, caches and provider objects need inventory and confirmed deletion; storage provider/access policy unresolved. |
| Detailed locations/local queues | Existing 30-day location retention remains independent. Its starting event is OD-16. Neither account recovery nor deletion restarts that clock or adds a blanket 30 days. |
| Communities/rides/chat/SOS | Shared content, authorship, leadership succession, orphan rows and emergency-history retention are unresolved. Define redact/delete/retain per category before erasure; do not drop shared tables by accidental cascading FKs. |
| Provider-held data, backups and replicas | Provider acknowledgement is not erasure. Restore must reapply a reviewed deletion ledger before reopening access. Ledger identifiers/hashes are not automatically anonymous; retention and legal exceptions need scope and expiry. |

A legal hold must identify the actual obligation, affected category, scope and
review/release condition. Retain only required data; continue other erasure and
normal location cleanup. Unresolved legal research is not a blanket hold or an
extension of detailed-location retention. These requirements are not a claim that
legal obligations, provider deletion or backup enforcement are implemented.

## Reviewable implementation sequence and acceptance evidence

1. After R1/model review: prepare transactional account/link and profile-text
   migrations and tests, with exact-identity bootstrap races and active-account
   resource checks. Do not add an unenforced photo reference: its storage/FK and
   public profile operations also depend on R4. A text-only development slice is
   not completion of PR-03. No public cross-user lookup.
2. After R2/R3: proof issuance/consumption and idempotency storage; deactivate/recover
   transactions, epoch invalidation and controlled-clock/race tests at both sides
   of the deadline. Reject stale proofs/jobs and later-cycle replay.
3. After R4: owned media, provider and shared-record deletion, scoped holds and restore
   suppression; test partial failures/retries, overdue work and every external copy.
4. Verify real development sign-in/session reload, deactivation with a still-signed
   token, authorized recovery, old-token rebootstrap rejection and key/revocation
   behavior. Run Android/offline/socket/media evidence when those consumers exist.

A simulated proof or local row deletion cannot close the provider/recovery/retention
gates. No migration/API implementation or phase acceptance follows from this draft.
