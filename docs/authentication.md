# Clerk authentication

Groupify uses `@clerk/expo` with the existing custom phone/OTP screens. Get Started opens sign-up; Log in opens sign-in. There are no prefilled phone numbers, test OTPs, or local authentication bypasses.

## Configuration

The selected Clerk application is `app_3LvhoAC44iCweTxKAX052qniNm3`. Use its existing development publishable key in `.env`:

```dotenv
EXPO_PUBLIC_CLERK_PUBLISHABLE_KEY=your_publishable_key
```

Only the publishable key belongs in the Expo client. No Clerk secret key is needed. Environment files are ignored by Git. Restart Expo after changing environment variables.

In that application's [Clerk Dashboard](https://dashboard.clerk.com/):

1. Enable phone sign-up, phone verification at sign-up, and phone sign-in using SMS codes.
2. Make phone the only required sign-up field for this flow. Required email, password, username, names, or legal acceptance need corresponding additional screens before enabling them.
3. Enable Native API under Native applications for Android/iOS.
4. Check allowed SMS countries for the numbers you plan to use.

These account settings are not changed by installing the SDK. The app displays provider errors when a method or SMS destination is disabled. The editable calling-code field accepts country codes such as `+1` or `+880`; pasting a complete international number in the phone field also works. Enter national numbers without a trunk prefix (for example `1712345678` with `+880`).

The Clerk CLI is not signed in or linked on this machine, so `clerk doctor` cannot validate Dashboard settings. That is separate from the client integration, which loads using the existing publishable key. Its generic missing-secret-key warning does not require adding a secret to this mobile app. To manage the selected application through the CLI later, sign in from your own terminal and link it:

```bash
npx --yes clerk@latest auth login
npx --yes clerk@latest link --app app_3LvhoAC44iCweTxKAX052qniNm3
```

## Behavior

- Clerk sends and verifies SMS codes for both new and existing accounts.
- Resend repeats the Clerk request and starts a 30-second cooldown after a successful send.
- Verification finalizes a session only when Clerk reports `complete`.
- `Stack.Protected` guards `/home` and sends signed-in users away from the auth screen. Session loading is resolved before rendering either route.
- SecureStore persists native sessions; Clerk manages its normal browser session storage on web.
- Sign out clears Clerk's session before protected navigation returns to authentication.
- Additional MFA/device-trust requirements and pending session tasks do not grant access. They currently show an explanation; dedicated task/MFA screens are outside this phone-only flow.
- The web sign-up form includes Clerk's CAPTCHA container when required by the instance's bot protection settings.

Protected screens only guard client navigation. Future backend endpoints must independently validate Clerk session tokens before returning private data.

## Run and verify

```bash
npm run web
# Or start an Android emulator, then:
npm run android

npm run typecheck
npm run lint
npm run test:auth
```

The auth tests use mocked Clerk resources and never send SMS or create users. To verify a real session, sign up with your own number, enter the received code, reload the app, sign out, and try opening `/home` while signed out. A wrong code must leave you on the verification screen. Existing custom development builds should be rebuilt after installing SecureStore; native project files remain generated by Expo.

References: [Expo quickstart](https://clerk.com/docs/expo/getting-started/quickstart), [phone OTP custom flow](https://clerk.com/docs/guides/development/custom-flows/authentication/email-sms-otp), [Expo protected routes](https://docs.expo.dev/router/advanced/protected/).

### Missing configuration at startup

When `EXPO_PUBLIC_CLERK_PUBLISHABLE_KEY` is absent, startup displays “Sign-in is unavailable” after fonts load and does not mount Clerk or protected routes. Set the development publishable key using the configuration above and restart Expo. This presentation does not validate a nonempty key or the remote Clerk application. No secret key is needed in the client.
